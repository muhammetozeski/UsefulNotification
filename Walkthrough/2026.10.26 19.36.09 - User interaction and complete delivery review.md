# User interaction and complete delivery review

UsefulNotification now has separated pending/scheduled/history pages, visible field groups, scoped history actions, and identity-based action/checklist editors. The user found the previous panel difficult to navigate and reported broken dragging. Static lifecycle checks had not covered actual mouse ownership or the clarity of the interface. Use [the interface guide](../Docs/Interface.md) before changing these workflows.

Posting a Windows modal move message still caused movement after button release in user testing. The user directed comparison with ShowPicOnly. Its explicit down/move/up cursor-delta model was adapted to the WebView pointer capture path, with cancellation on release, capture loss and blur. The user then requested removal of the remaining light outer frame. Native inspection found a 16-pixel window/client dimension difference, matching eight pixels on each side. Returning the full client rectangle for WM_NCCALCSIZE removed it; the user confirmed the frame was gone and described a minor line during motion as unimportant.

An earlier corrected build failed to open because LINQ enumeration of DisplayArea.FindAll threw InvalidCastException in the WinRT projection. Count/index access fixed both saved-placement restoration and monitor choices. A process launch alone had been called an opened panel; subsequent startup checks included broker acceptance and a visible native handle. Preserve that distinction.

The final functional review found and corrected stale hover-release pauses, sound drafts overwriting current placement, history deletion affecting future repeats, invalid checklist identities, unsupported image schemes, and null collection/required-theme validation. Stable tag-upsert request identities now retain their original acceptance even after a later request and broker restart. Portable storage has its own path converters: owned template/audio/image/executable paths relocate, while wire paths and external files keep their meaning. The 2,000-entry response was about 2.3 million characters and exceeded the old shared one-million-character read limit; an independent client response budget fixed listing while retaining the inbound limit.

Evidence is disposable under C:\C\UsefulNotificationApi. Final runs passed 42 Core behavior checks, 13 actual Razor-handler/render checks, seven pointer lifecycle checks, focused acceptance/validation cases, 17 portable-path cases, the 2,000-entry response case, and 14 relocated Release checks against the real Windows renderer. Additional checks covered queue promotion, snooze, delivery deadline recurrence, callback equality, old records, wait cancellation and shutdown with a connected incomplete peer. Independent source review rechecked its findings. Server-rendered component images were inspected separately from native mouse feedback. Copying and signing do not require repeating unchanged behavior checks.

The public Core XML, paired language resources, normal Visual Studio MSBuild restore, clean publishing stage, signed apphosts and portable layout remain part of delivery. See [Build](../Docs/Build.md), [Integration](../Docs/Integration.md), and [Interface](../Docs/Interface.md); their maintained instructions replace rediscovering these issues from logs.
